# 22 · 从评估集到生产验收

[返回目录](../README.md) · [评估基础](12-evaluation.md)

## 先定义任务单位与正确性

一个用户问题可以有多条关键断言、多个证据来源和几次工具操作。句子正确率、断言正确率和完整任务成功率分母不同，不能混用。

例如回答包含三个正确结论和一个错误金额：按四条断言是 75%，但按业务任务可能整体不合格。应预先定义关键错误是否导致整题失败。

## 一个可复核样例怎样写？

```json
{
  "case_id": "POLICY-017",
  "question": "指定地区与日期的住宿限额是多少？",
  "identity": "employee-demo",
  "data_snapshot": "policy-demo-v2",
  "required_evidence": ["section-4-condition", "section-4-limit"],
  "required_claims": ["适用地区", "有效日期", "金额与单位"],
  "allowed_tools": ["search_policy"],
  "expected_behavior": "证据不足时澄清，不生成金额",
  "critical_failures": ["越权读取", "编造金额", "重复写入"]
}
```

标签要表达可接受行为，而不是只保存一段唯一参考答案。不同措辞可以同样正确，缺少必要条件也可能让语言相似的答案不合格。

## 检索指标的分母必须清楚

Recall@k 可以定义为正确证据集合中有多少进入前 k 个候选。某题需要两个片段，检到一个不等于完整可答。

Hit@k 可只判断是否命中至少一个正确项；MRR 关注第一个相关项的位置；nDCG 可表达多级相关性和排序质量。选什么取决于你的证据标签。

文档级、片段级和完整证据集合级结果可能不同。报告时写清层级，避免利用粗粒度命中掩盖关键条款遗漏。

## 生成质量应拆成几项

| 指标 | 一个可用定义 | 不能替代什么 |
| --- | --- | --- |
| 结论正确率 | 满足业务事实标准的样例比例 | 来源支持 |
| 断言支持率 | 有证据支持的关键断言 / 全部关键断言 | 证据是否完整 |
| 引用正确率 | 确实支持关联断言的引用 / 所有引用 | 答案是否漏掉关键信息 |
| 引用覆盖率 | 被正确引用支持的需引用断言 / 全部需引用断言 | 事实本身是否最新 |
| 无答案处理正确率 | 在不可答样例中恰当澄清或说明缺失 | 可答题的成功率 |

不要只优化拒答率：模型对所有问题都说「不知道」，可能在缺失信息样例很好，却没有完成可答业务。

## 工具与 Agent 要评估轨迹

除了最终答案，还要检查工具是否允许、参数是否正确、有没有重复效果、是否使用当前证据、有没有陷入循环，以及错误后是否恢复。

一次任务最后成功，但中途发生越权访问，不能被最终成功掩盖。预算耗尽、等待人工确认、结果未知和明确失败，也应分开统计。

对于写操作，观察实际业务效果而不只数工具调用。两次调用可能只有一次效果，也可能一次调用被后端重复处理。

## Agent 分数同时测到了模型、Harness 与环境

模型调用之外，工具集合、上下文压缩、测试脚本、CPU/内存配额、网络和超时都会影响最终任务结果。[Anthropic 基础设施噪声研究（2026-02）](https://www.anthropic.com/engineering/infrastructure-noise)显示，仅改变环境资源就能显著改变 Agent 编程评估成绩；其具体差值属于原实验，不作为通用修正系数。

可比较评估应固定任务/数据划分、模型与模板、Harness、工具/镜像、验证器、资源和预算；改变其中一项时记录实际配置。环境失效、模型错误、判分失败和结果未知分别报告。确认基础设施失败后的重跑应保留原 attempt 与统一规则，不能只对某个模型选择性补考，也不能删除全部困难失败后再比较成功率。

把最终产物、动作轨迹和最终环境状态分别判定：结果正确但越权或改写验收条件，不能算合格；轨迹遵守边界但环境故障，也不宜当作纯能力失败。候选覆盖率与最终选择成功率分别记录，避免用“多个候选里有一个正确”替代真实交付。可观测配置关联见[第 31 章](31-ai-systems-observability-and-debugging.md)。

## 模型裁判怎样降低偏差？

先定义量规、事实来源与失败类别；用人工样例校准，再检查模型裁判与人工的分歧。

将两个答案的顺序互换可以检查位置偏好；控制答案长度和格式可以检查风格偏好。对于代码与计算，优先使用可执行验证；对于证据支持，明确给出需要判断的断言和来源。

裁判输出应包含标签和可核对理由，但理由本身仍可能错。模型对自己评分，也不形成独立可靠证据。

## 故障注入比只测正常路径更重要

至少测试：无资料、过期资料、权限拒绝、恶意外部文本、模型输出不合法、工具超时、写成功但回执丢失、进程重启、并发重复、预算耗尽和用户修改目标。

为每种故障预先定义允许行为。例如写操作结果未知时应对账或挂起，而不是返回成功；证据缺少适用条件时应澄清，而不是猜测默认条件。

## 线上指标与离线质量要连接

发布验收绑定任务 trace 与实际资产版本，评估质量/错误和合格成本；请求/训练 trace、timeline、profiling 及版本血缘的关联机制由[第 31 章](31-ai-systems-observability-and-debugging.md)主责。工具耗时与模型耗时要能回到同一任务，不能以单模型指标代替任务结果。

最终看「每个合格任务的成本」：便宜模型若频繁重试或人工修订，可能比较贵但成功率高的模型更昂贵。

只看平均延迟也可能掩盖长请求与少数用户的严重尾延迟。按任务类型、长度、权限和失败类别分组，但避免分组过细导致样本不足。

## 一个发布验收流程

1. 固定版本，运行开发集与独立留出集。
2. 核对关键事实、来源和权限等硬性要求。
3. 运行故障与恢复案例，确认状态和业务效果。
4. 用真实长度分布压测，检查容量和尾延迟。
5. 小范围放量，观察质量、成本与失败类型。
6. 明确回退版本与数据兼容性，再逐步扩大使用范围。

线上试验和观察需要符合具体业务的数据与权限要求。这里描述的是验收机制，不替代组织自身的发布流程。

## 将评估变成改进证据

| 错误集中位置 | 优先改动 |
| --- | --- |
| 文档抽取与证据召回 | 解析、分块、检索与版本过滤 |
| 条件判断与证据组织 | 查询澄清、上下文与指令 |
| 算术与结构化操作 | 确定性工具与参数校验 |
| 长流程漂移或循环 | 计划、状态、终止与预算 |
| 重复写入或错误恢复 | 后端幂等、事件记录与对账 |
| 排队和缓存耗尽 | 调度、准入与容量配置 |

每次改动先写出预期改善的失败类型，再做对照。把所有错误都归结成「模型不够聪明」，通常无法产生有效工程动作。

## 样本不确定性与配对比较

有限样本的比例存在不确定性，区间估计描述一定统计假设下的证据强度。它不能修复有偏抽样、重复案例或错误标签，也不能将常规问答成绩推广到所有极端失败。

两个版本在同一批案例上比较，应关注由错变对与由对变错的分歧，而非只看两个总分。配对设计利用相同任务减少部分差异，仍要检查生成随机性与多次运行波动。

显著性不等于业务价值，小差异可能在大样本上显著却没有实际收益；重要领域退化也可能被平均分掩盖。任务风险、成本与效果大小需要一起报告。

## 负载模型与容量

闭环请求等上一个完成后再发，可能掩盖真实持续到达时的队列增长；开放到达过程按外部速率发请求，更容易暴露过载。两种负载回答不同问题。

容量判断包括长度分布、突发、长请求、取消、模型预热和缓存状态。只测稳定短请求无法证明生产容量。拒绝率、重试与超时也是体验指标，不应只保留成功请求统计。

统一的 TTFT、TPOT/ITL、分位延迟、useful throughput 与 SLO-driven capacity planning 见[第 30 章](30-ai-systems-performance.md)。发布时固定 Compiler/Runtime 与引擎版本，记录图/编译冷热和资源 placement；这些因素会让同模型同精度表现不同。执行栈见[第 28 章](28-ai-compiler-and-runtime.md)，GPU/NIC 调度、组级就绪与扩缩容见[第 29 章](29-ai-platform-and-cluster-scheduling.md)。

## 故障恢复与发布结果

进程恢复、业务对账、缓存回收和权限撤销需要独立检查。任务最终成功不能掩盖中间越权或重复写入；重试后得到一个答案，也不证明状态已经正确恢复。

发布后的观察将失败关联到模型、Prompt、数据、工具与引擎版本。回退要明确资产与持久状态兼容，已发生副作用按业务流程处理，不能由模型版本回退自动消失。
